# 初始化时序与安全复核

2026-11-03。用户要求继续排查设置重置，尽量不增加 Hook，并同时考虑安全性。
本轮仅在电脑执行，未连接手机、未修改游戏数据、未发布修复包。

## 可排查的初始化差异

旧 LSP 经 luaopen_pb 返回的函数表取得 encode，再安装编码回调。
Root 版通过已确认客户端的固定注册表生成 encode 地址，在发现目标库后安装。
完整启动时序不同，但不等于编码函数身份不同。

已对 SHA-256 为
`7f61316eb49e95e416b2a96b744b3eb0cc94d9347bf3c3f5c5cf983bb18a05a6`
的本地 libtolua.so 检查实际 luaopen_pb（0x1b3f0）机器码：
初始化从 0xb19a0 复制注册表，再通过注册 API 暴露 pb 函数。
该表内 encode 地址为 0x1bd60，与 Root 生成配置一致。

新增 `minimal-root/tests/registration_lifecycle_test.py`：

- 对本地 ELF 的 PT_LOAD 与相对重定位建立 ARM64 CPU 仿真。
- 运行真实 luaopen_pb 指令；只替换其调用到的 memcpy 和外部 Lua API。
  memcpy 复制实际注册表，Lua 注册接口记录实际传入的条目。
- 对元表已存在/新建两个分支，分别模拟编码入口修改前/修改后，共四次执行。
- 确认初始化正常返回一个 Lua 结果，encode 注册地址始终为同一地址，
  初始化不执行 encode，也不覆盖入口字节。
- 只写仿真内存，不写库文件或手机；只有合成状态，不读取凭据。

运行：
`uv run --with pyelftools --with unicorn python minimal-root/tests/registration_lifecycle_test.py`

结果：1 项测试（4 次初始化）通过。这是指定 ELF 的注册流程证据，
不是完整 Lua VM 启动、多线程 Android 或设置持久化验证。
因此降低了“安装较早导致函数被初始化替换/选错入口”的可能性；
没有排除安装期间并发、其他初始化依赖或手机实际版本与本地材料不同。

## 安全检查与仍存在的限制

- 本轮不新增或恢复任何 Hook，不添加证书、代理、保存轮询或配置回写。
- 现有原函数跳板 3 项 CPU 测试通过，包括多组寄存器/栈状态、分支与返回验证。
- 重新编译并执行 fixed_patch_test：参数/入口拒绝、写权限失败、RX 恢复失败、
  原字节回滚和重复 RX 失败等 7 组场景通过。
- 这些测试仅说明检查过的顺序执行与失败分支符合预期。
- **已知限制：固定跳板版写 16 字节入口不是原子修改，也没有暂停其他执行线程。**
  dl_iterate_phdr 的库枚举锁不能证明其他线程不执行该函数。
  installed 屏障也只对已完整进入替换回调的线程有效，不能保护正在执行部分改写指令的线程。
- 写入期间短暂 RWX 仍存在；如果权限恢复与再次恢复均失败，代码虽尝试回滚，
  仍不能声称内存权限已恢复。现有诊断会报告该情况。
- 未通过设备证据证明上述限制导致灵敏度重置，不能将它当作已确认根因。
- 不对 Android 线程运行时盲目发信号/挂起，不使用不受支持的 ART 内部接口，
  不以消除竞态为由引入未经验证的全局线程控制或大批额外 Hook。
- 代码正确性、内存/数据安全与游戏风控是不同问题；本轮测试不证明不会封号。

## 当前决定

保持单个业务入口，暂不修改运行时。原成功包与原 LSP 保留。
只有确认某个时序差异对设置读写产生影响后，才对该差异作最小修补。
不把未知原因用额外保存 Hook、删除缓存、固定延时或伪造角色缓存掩盖。
设置重置仍未修复，完整实机验收仍缺失。
