# 0.4.0 与 Root 版本的业务对照

2026-11-03，按用户要求在电脑上进行；未连接或操作手机。

## 参照物身份

本机保留的 `Minifire-Compat-0.4.0.apk` 与 `Minifire-Compat-0.4.1.apk`
内 `lib/arm64-v8a/libminifire_login.so` 均为 372024 字节，SHA-256 均为：

`470656623b7a06dbc266e5f6079cbfd29b702bc83b1672ca1dd4576fb2d18e4e`

归档工程的 stripped 原生库也具有同一摘要。归档工程与仓库的旧版
`native_entry.cpp` 对比无差异，旧版 `login_filter.cpp` 对比当前源码仅有
下述版本字段及缓存识别差异。因此这次参照包含 0.4.0 的实际 APK，
不是仅凭 0.4.1 名称推测。相同原生库不表示两个 APK 的 Java/UI 完全相同。

## 业务对照

| 项目 | 原 0.4.0 | 当前 Root | 对照结果 |
|---|---|---|---|
| 终端登录 | `md.ApiLoginRequest` | 同名消息 | 相同 |
| 大厅登录 | `md.Login` | 同名消息 | 相同 |
| 平台字段 | 各消息分别处理 `PhoneOs` / `Phone_Os` | 同样处理 | 相同 |
| 渠道字段 | 对已确认渠道执行兼容转换 | 同样的输入守卫与转换 | 相同 |
| 登录版本声明 | `1.0.78` | `1.0.79` | 有意更新；不是修改全局 Android 客户端版本 |
| 缓存版本 | 识别已知 77/78 组合 | 增加已知 79 组合 | 有意扩展，避免缓存重登被拒绝 |
| 非登录消息 | 不修改 | 不修改 | 相同，包含资源版本请求 |
| 请求表 | 直接修改传入表 | 直接修改传入表 | 相同；没有新增克隆或还原流程 |
| 响应处理 | decode 后读取终端响应 Code 作为诊断 | 未 Hook decode | 原版此处只有观察，没有字段回写 |
| 设置文件 | 过滤器不操作 | 过滤器不操作 | 仍不能据此排除间接影响 |

原版依赖 LSPosed 的库加载通知，先经 `luaopen_pb` 找到编码入口，再安装
encode/decode 回调。Root 版通过 Zygisk 加载，等待并验证库后安装单个编码回调。
加载和安装过程不相同，不能仅靠过滤器相同断言生命周期相同。

这次另检查了当前 `service.sh`、`customize.sh`、`control.sh`、`config.sh`、
`collector.sh`：其写入对象为模块自己的开关、目标包和诊断；没有清除游戏数据、
删除 PlayerPrefs、自动强制结束游戏或恢复游戏云设置的命令。升级时旧代理的清理
属于独立迁移路径；这次没有在设备执行，也没有重新启用旧代理。

## 可重复的电脑验证

运行：`uv run python tools/verify_legacy_parity.py`

工具从 Git 标签 `v0.4.1` 读取旧过滤器，与当前生产过滤器分别编译，使用本地真实
Lua 5.1 / Protobuf fixture 运行。全部数据为合成内容，无联网、无手机读取。
APK 存在时另校验上述原生库摘要相同。

- 864 组旧版已覆盖输入：4 种消息、6 种模式、3 种平台、3 种渠道、4 种版本组合。
- 6 组新增的 1.0.79 缓存输入，参照相应旧版可接受的缓存组合。
- 比较整个请求表，并对两个登录消息执行实际编码、解码后比较全部协议字段。
- 断言合成凭据、`BattleSet`、`BattleSetWithUID` 未被修改。
- 只将旧版**输出**中的预期版本转换纳入差异豁免；不更改实际生产实现。
- Protobuf 字段顺序不属于语义，比较解码后的值，不要求编码字节排列相同。

结果：**870 组通过**；现有过滤器测试 **22 项**及库身份守卫 **5 项**也通过。
本机结果写入忽略目录 `minimal-root/build/legacy-parity/result.json`。

## 对设置重置问题的实际意义

“保留原业务，仅换加载方式并更新版本声明”已经是当前源码的实现事实。
尚未发现一个能够通过重新复制旧过滤器解决的额外业务差异。
这份结果不证明手机上设置持久化正常，也不证明它与模块无关。

当前不能用删除设置、强制覆盖缓存、改回旧版本声明或追加保存 Hook 充当已确认修复。
剩余重点是启动/安装时机、缓存角色选择，以及保存至磁盘与重新加载的实际边界。
设备证据仍待取得，详见 `SETTINGS-PERSISTENCE-INVESTIGATION.md`。

本次不改动运行时，不生成新的“设置已修复”包，也不改变原成功包。

## 补充：完整网络链路与包名选择复核

用户进一步要求确认不能仅以过滤器相同代表整个网络链路相同，并提出包名选择可能有关。

1. 旧工程 Java 的 `mobileLogin` / `doWrapResponse` 回调调用原方法，记录是否登录及结果码，
   没有替换参数、SDK 渠道、返回值或凭据。Root 版没有这两个观察回调。
2. 本地游戏 `ServerManager` 样本中，终端路径为构造请求表 → `pb.encode` →
   由游戏生成签名 → 由游戏发送。两版过滤器均处于编码入口，未另外实现签名或请求发送。
   服务端返回的大厅地址与 Token 继续由游戏自己处理。这是本地样本的静态链路证据，
   不是当前手机完整抓包证据。
3. 旧版 decode 回调只读取 `md.ApiLoginResponse.Code` 并恢复 Lua 栈，未修改响应表。
   Root 版没有响应改写逻辑。因此不能说原版存在“把苹果响应版本改回安卓”的转换被漏移植。
4. 2.0.1 成功包的 ZIP 内没有旧代理服务或证书材料；启动脚本明确不使用代理或证书挂载。
   它与当前源码的过滤器没有差异。模块和 Root companion 的 socket 是本地配置通信，
   不承担游戏网络转发。升级清理旧版状态不等于已证明手机没有其他历史残留。
5. 旧版由框架配置选择 mode 3/4/5，默认恢复 mode 5；Root 固定 mode 5。
   本次差分测试分别覆盖各模式，但没有从手机读取当初实际保存的模式，不能把旧版所有
   可选模式都称作与 Root 完全一致。
6. 目标包选择的调用链：WebUI 显式保存 → `control.sh target` → 写模块自身的
   `target_package`、关闭 `game_enabled` → 下次进程启动由 Root companion 核对包名和 UID。
   编码回调未把该字符串传入过滤器。它不改 Android 的 `Application.identifier`、
   请求 `PackageName` 或游戏 `app_data_dir`，不重命名/清除游戏设置。
7. 已确认选择功能的边界：保存相同包名也会关闭兼容；正在运行的进程不会即时卸载回调。
   读取状态、刷新应用和诊断不触发 target 保存。新增测试验证这些读取操作后，模块包名和
   开关文件的内容、修改时间与 inode 均不变。
8. 选择另一实际 APK 或另一 Android 用户/分身会对应不同数据环境；选择界面不迁移设置。
   同一包名的多用户实例也没有在界面细分选择。包名可选不是所有渠道协议已适配的证明。

准确结论：在相同客户端、相同输入、相同 mode 5 且回调已成功安装的条件下，除已列出的
版本与缓存兼容差异，两版对登录协议字段的处理等价。没有证据证明完整线上会话、
服务端响应、安装时机、当时配置或本地设置生命周期完全相同。包名选择尚未被证实为
设置重置根因，也没有被设备证据彻底排除。
